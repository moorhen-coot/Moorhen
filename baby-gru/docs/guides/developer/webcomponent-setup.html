Embedding the WebComponent in a plain page

This guide walks through a minimal, runnable integration of the Moorhen WebComponent in a host page written in plain TypeScript/JavaScript. It covers what you need to get started: serving the Moorhen assets, and registering the element and waiting until it is ready. Loading data and controlling the view are the same for every framework, and are covered in Loading data and the MoorhenInstance API.

Prerequisite: you should be comfortable with the concepts and the module layout described in The Moorhen WebComponent. In particular we import everything from the moorhen/web-component sub-path. There is no bare moorhen import.

1. Install the package and copy the Moorhen assets

Install moorhen in your project:

npm install moorhen

The element needs static assets (styles, icons and WebAssembly binaries) at runtime. Copy them from the installed package into the public/ folder of your own project, so they are served from /MoorhenAssets/...: 

cp -r node_modules/moorhen/public/MoorhenAssets public/

Important: copy the assets again after every Moorhen update, because the WebAssembly binaries inside MoorhenAssets can change in any version.

A Vite plugin that automates this copy is planned but not usable yet. Copy the assets manually for now. If you serve them from a different path, set the url-prefix attribute on the element (see Element attributes below).

Technical note: because Moorhen runs WebAssembly in web workers, you must serve the page over HTTP(S) with the cross-origin isolation headers described in section 2, rather than opening the file directly from disk.

2. Serve the page with cross-origin isolation

Moorhen's Coot/CCP4 code is compiled with WebAssembly threads, which need SharedArrayBuffer. Browsers only expose SharedArrayBuffer to pages that are cross-origin isolated, so the server hosting your page must send these two response headers: 

Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp

Without them the page is not isolated and Moorhen's Coot worker cannot allocate its shared memory, so the component will not start. Check the result in the browser console: window.crossOriginIsolated must be true.

require-corp also affects CORS: any cross-origin resource the page loads (scripts, styles, fonts, workers, WebAssembly) must opt in with CORS or a Cross-Origin-Resource-Policy header. Serving MoorhenAssets from your own origin is the simplest way to satisfy that.

Vite

Add the headers to both the dev server and the preview server:

// vite.config.ts
export default defineConfig({
    server: {
        headers: {
            "Cross-Origin-Opener-Policy": "same-origin",
            "Cross-Origin-Embedder-Policy": "require-corp",
        },
    },
    preview: {
        headers: {
            "Cross-Origin-Opener-Policy": "same-origin",
            "Cross-Origin-Embedder-Policy": "require-corp",
        },
    },
});

nginx

add_header 'Cross-Origin-Opener-Policy' 'same-origin';
add_header 'Cross-Origin-Embedder-Policy' 'require-corp';

Python HTTP server

from http.server import HTTPServer, SimpleHTTPRequestHandler, test
import sys

class CORSRequestHandler (SimpleHTTPRequestHandler):
    def end_headers (self):
        self.send_header('Cross-Origin-Opener-Policy', 'same-origin')
        self.send_header('Cross-Origin-Embedder-Policy', 'require-corp')
        SimpleHTTPRequestHandler.end_headers(self)

if __name__ == '__main__':
    test(CORSRequestHandler, HTTPServer, port=int(sys.argv[1]) if len(sys.argv) > 1 else 8000)

Static hosts: some hosts (for example GitHub Pages) do not allow you to set response headers. You then need a service-worker shim (such as coi-serviceworker) to add them, or host the page where headers can be configured.

3. The host HTML page

Start from a very small page. The important parts are the <moorhen-web-component> element (give it a unique id and a size) and a module script that imports your entry point: 

<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <title>My Moorhen page</title>
  </head>
  <body>
    <h1>Moorhen</h1>

    <p id="loading-text">No structure loaded yet.</p>

    <moorhen-web-component id="moorhen-1" width="1000" height="800"></moorhen-web-component>

    <button id="load-7avk">Load 7AVK (PDBe)</button>
    <button id="center-residue-1231">Centre on residue 1231</button>

    <script type="module" src="./main.ts"></script>
  </body>
</html>

The buttons and the paragraph are plain HTML hooks, shown here to sketch a typical host page. The Moorhen API calls that would drive them are the same in every framework and are covered in Loading data and the MoorhenInstance API. Here main.ts is your module entry point (transpile it to JavaScript for production, as you would with any TypeScript project).

4. Register the element and obtain the instance

First, register the custom element and grab a strongly-typed reference to it. Then wait for Moorhen to be ready with getMoorhenInstance(), which resolves to the MoorhenInstance you will use for everything else: 

import { registerMoorhenWebComponent, MoorhenWebComponent } from "moorhen/web-component";

// Define the <moorhen-web-component> custom element (idempotent).
registerMoorhenWebComponent();

// A typed handle on the element we put in the HTML above.
const moorhen = document.getElementById("moorhen-1") as MoorhenWebComponent;

// Resolves once Moorhen has finished mounting (wasm downloaded, scene built).
const moorhenInstance = await moorhen.getMoorhenInstance();

getMoorhenInstance() resolves immediately if the element is already ready, otherwise it waits until it is. The same readiness is also exposed as the boolean property element.ready, and a moorhenReady CustomEvent is dispatched on window (its detail.id is the element id). See the MoorhenWebComponent API page. Because we call it at the top level of a module, await is fine here.

5. Element attributes

The custom element accepts a few HTML attributes that change how it is set up:

Attribute Property Purpose
width / height width / height Fixed pixel size for the rendered Moorhen UI, e.g. "1000" / "800". Leave both out to follow the size of the container instead, see Sizing the element.
url-prefix urlPrefix Base path of the Moorhen assets (default "MoorhenAssets"). Set it if you did not copy the assets to public/MoorhenAssets.
view-only viewOnly Set to "true" to hide editing features and expose a view-only UI.
disable-file-uploads disableFileUploads Set to "true" to prevent the user from loading files through the UI.

For example, a view-only element whose assets live under a custom prefix:

<moorhen-web-component
    id="moorhen-2"
    width="900"
    height="700"
    url-prefix="/static/MoorhenAssets"
    view-only="true">
</moorhen-web-component>

Sizing the element

There are two ways to size the component, and they behave differently:

  • A fixed size. Set width and height, and Moorhen lays itself out at exactly those pixel dimensions.
  • Follow the container. Leave both attributes out, and Moorhen measures the element and follows it with a ResizeObserver, so the view grows and shrinks with its container.

For the second option the element must actually have a size, otherwise it measures zero and falls back to the window dimensions (with a warning in the console). The element sets display: block, width: 100%, flex: 1 1 auto, min-width: 0 and min-height: 0 on itself, so the simplest approach is to let it fill a sized parent: 

<div class="viewer">
    <moorhen-web-component id="moorhen-1"></moorhen-web-component>
</div>
.viewer {
    display: flex;
    height: 70vh;   /* the container needs a definite height */
}

Sizing the element directly, with an inline style, works too:

<moorhen-web-component id="moorhen-1" style="width: 900px; height: 320px"></moorhen-web-component>

Gotcha: use the style attribute rather than a stylesheet rule when sizing by hand. The element sets an inline width: 100% on itself, and an inline style beats a stylesheet, so moorhen-web-component { width: 900px } in your CSS is ignored. height is not set by the element, so a stylesheet height works as usual.

Fixed size and overflow: with width/height set, the element’s own box stays width: 100%. If you choose a size wider than the space available, the view overflows rather than shrinking, so put the element in a container that can scroll.
